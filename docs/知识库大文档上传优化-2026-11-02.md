# 知识库大文档上传优化（50 万字场景）

## 一、先量基线，再动手

优化前用 50 万字中文文档（1.41MB，2387 段）实测走完整上传链路：

| 阶段 | 耗时 | 占比 |
|---|---|---|
| 解析 | 0.05s | 0.3% |
| 切块 | 0.01s | 0.1% |
| **向量化** | **13.58s** | **92%** |
| 写向量库 | 1.12s | 7.6% |
| 合计（管道） | 14.77s | |
| **HTTP 端到端** | **21.49s** | 含首次模型加载 |

结论：**瓶颈在向量化，且已经打满 CPU**。

## 二、先排除"看起来能提速"的方案

为了避免拍脑袋调参，把常见优化手段都实测了一遍（512 块 × 976 字）：

| 方案 | 吞吐 | 相对基线 |
|---|---|---|
| chroma 内置 EF（batch=32） | 38.1 块/秒 | 基线 |
| 自建 ONNX，batch=32 | 40.3 块/秒 | 1.06x |
| 自建 ONNX，batch=128 | 40.5 块/秒 | 1.06x |
| 自建 ONNX，batch=512 | 38.0 块/秒 | 1.00x |
| 自建 ONNX，intra_op=8 线程，batch=128 | 40.9 块/秒 | 1.07x |
| 4 个并发任务共享 1 个会话 | 34.4 块/秒 | 0.90x |
| 6 个并发任务共享 1 个会话 | 41.8 块/秒 | 1.10x |

**加大 batch、加线程、加并发全部无效**（≤1.1x，部分更慢）。这台 6800H 上 MiniLM 单会话已经吃满，40 块/秒就是天花板。

同时核对了分词情况：976 个汉字 ≈ 780 token，模型上限 256 token，**确实存在截断**——但这是检索质量问题，不影响上传速度，本轮不动（改动会牵连已有向量的一致性）。

## 三、所以优化的是架构，不是算力

真正的问题不是"慢 20 秒"，而是这 20 秒里：

1. HTTP 请求被全程占住，前端只能看到转圈
2. 前端 axios 超时 180 秒，超过就误判失败（后端其实还在跑）
3. 失败就得整份重传
4. 一次只能传一个文件

### 改动

**上传接口只做「校验 + 落盘 + 建记录」**

```
POST /api/admin/knowledge/upload        → 0.83s 返回 {id, status: chunking, progress: 0}
POST /api/admin/knowledge/upload-batch  → 0.84s 返回 {uploaded: [...], rejected: [...]}
```

**后台摄入任务按批写库并上报进度**

```python
for start in range(0, total, 32):        # 32 块一批 ≈ 0.8 秒
    vectors = await embedding.embed_batch(...)
    vectorstore.upsert_chunks(...)
    doc.processed_chunks = written
    doc.progress = min(99, written * 100 // total)
    await db.commit()
```

进度封顶 99%，最后落库成功才置 100，避免"100% 但还没启用"的错觉。

**串行队列**：全局 `asyncio.Lock`，多文件排队入库。实测并发无收益（0.9x），串行反而让进度可预期。

**失败可重试**：`POST /api/admin/knowledge/{id}/retry` 复用已保存的原文件，不用重传。

**孤儿清理**：进程内后台任务在服务重启时会凭空消失，DB 里的 `CHUNKING` 会永远转圈。启动时统一标记失败并给出可重试提示。

## 四、实测结果

### 单文件 50 万字

| 指标 | 优化前 | 优化后 |
|---|---|---|
| 上传接口返回 | **21.49s**（阻塞） | **0.83s** |
| 入库完成 | 21.49s（同步） | 20.6s（后台） |
| 进度可见 | 无 | 每 1.3 秒一次，单调递增 0→6→12→25→…→93→100 |
| 超时风险 | 有（180s 上限） | 无 |

## 五、能力边界（要如实告知）

1. **总量耗时没变**：50 万字仍是 20 秒左右，只是不再阻塞用户、不再超时。
2. **向量化吞吐是硬上限**：约 40 块/秒（本地 MiniLM，CPU）。要更快只能换机器、换在线 embedding，或换更小的模型。
3. **单次最多 20 个文件**（`MAX_BATCH_FILES`），单文件 ≤ 50MB。
4. **串行入库**：一次提交 5 个 50 万字文档，要排队约 100 秒，进度会逐个推进，不会并行加速。
