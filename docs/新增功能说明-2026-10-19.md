# 新增功能说明（2026-10-19）

本轮在原有 P0/P1 基础上补充 10 项能力，均已通过运行态验证。

---

## 一、审查模板（可配置审查维度）

**解决的问题**：原来 9 个审查维度写死在 `app/rag/retriever.py`，采购合同和劳动合同套同一套标准。

- 新表 `review_templates`，字段：名称、说明、维度 JSON、是否默认
- 发起审查时传 `template_id`（不传走默认模板），报告会存模板名快照
- 管理入口：侧边栏「审查模板」→ 维度可增删改，支持设为默认

接口：`GET/POST /api/templates`、`PUT/DELETE /api/templates/{id}`
验证：新建「采购合同专项」（3 个维度）→ 用它审查 → 报告 `template_name` 正确回填。

---

## 二、合同版本比对 + 问题闭环

**解决的问题**：合同改完要重传，法务真正关心的是"上轮提的问题改了没有"。

- `Contract` 新增 `version` / `root_contract_id` / `parent_contract_id`
- 上传新版本：`POST /api/contracts/{id}/versions`（旧版本保留）
- 比对：`GET /api/contracts/{id}/diff`
  - 段落级 diff：新增 / 删除 / 改写 / 未变的段数 + 明细
  - 问题闭环：上一版每条风险项逐条判定

**闭环判定口径（保守，不谎报"已修复"）**

| 状态 | 条件 |
|---|---|
| 仍存在 | 旧片段在新版原文中原样出现 |
| 已改写待确认 | 片段消失，但存在相似度 ≥0.75 的段落 |
| 疑似已修复 | 片段消失且无相似段落 |
| 需人工复核 | 旧风险项本身没有原文片段（如条款缺失类） |

验证：v3→v4 实测「付款条款/争议解决」判为疑似已修复、「违约责任」判为仍存在，与人工改动一致。

## 三、任务中心

**解决的问题**：批量上传后只能一份份点审查，失败任务散落在列表里。

- `GET /api/tasks`：按 进行中 / 失败 / 待审查 / 解析失败 四类聚合
- `POST /api/tasks/batch-review`：批量提交（单次上限 20，单个失败不中断）
- 前端页面每 5 秒自动刷新，支持勾选 + 选模板批量发起

验证：批量提交 2 份 → `accepted=1 / skipped=1`（跳过的是已定稿的），失败原因随响应返回。

---

## 四、追问引用卡片

**解决的问题**：PRD 4.4 要求"引用合同原文或知识条目要展示可点击卡片"，此前证据只塞进 prompt，用户看不到。

- `stream_chat_answer` 新增 `citations_out`，把命中的知识条目回传
- WebSocket `done` 帧带 `citations`，前端渲染为可展开卡片（文件名 + 相似度 + 原文）
- 对话检索阈值从 0.55 调到 0.30（本地 embedding 中文偏弱，0.55 会导致永远无依据）

验证：追问「付款条款有哪些风险」→ 返回 2 条引用，页面显示 50% / 31% 两张卡片。

## 五、报告定稿

- `Review` 新增 `finalized_at` / `finalized_by`
- `POST /api/reviews/{id}/finalize?finalize=true|false`
- 定稿后：风险项 `PATCH` 返回 400、重新审查返回 400
- 前端顶部显示「已定稿」标签，按钮切换为「取消定稿」

验证：定稿 → 改风险项 400 → 重审 400 → 取消定稿 200。

## 六、报告页风险项筛选

左侧风险项支持按「等级」「处置状态」两个维度过滤，标题显示 `已显示/总数`。

## 七、启动时清理孤儿任务

服务重启后，内存中的后台任务消失，DB 里 `RUNNING` 会永远卡住。
`main.py` 的 lifespan 启动时统一把残留 `RUNNING` 标记为 failed（附原因），并把合同状态从 `REVIEWING` 退回 `PARSED`。

---

## 八、限流与用量统计

**限流**（进程内滑动窗口，配置在 `.env`）

```ini
RATE_LIMIT_REVIEW_PER_MINUTE=10   # 发起审查
RATE_LIMIT_CHAT_PER_MINUTE=30     # 追问
```

超限返回 429（`AppError code=429`），提示需等待秒数。

**用量统计**

- 新表 `llm_usages`：场景、模型、prompt/completion/total tokens、耗时、是否成功
- `GET /api/admin/usage-stats?days=7`：按场景聚合 + 按天趋势
- 前端「用量统计」页：调用次数、token、平均耗时、场景占比条

> 说明：非流式调用能拿到准确 token；流式追问只记录次数与耗时（需服务端开启 `stream_options.include_usage` 才能统计 token）。

## 九、上传文件魔数校验

`app/core/file_guard.py` 读文件头判断真实类型，与扩展名比对：

- PDF：`%PDF`
- DOCX：ZIP 容器且含 `word/`
- PNG/JPG：固定魔数
- TXT/MD：前 4KB 不能含 NUL 字节

验证：README.md 改名成 `.docx` 上传 → 400「文件内容与扩展名不符」。

---

## 十、并发审查去重

`create_review` 对合同行加 `SELECT ... FOR UPDATE`，同一合同并发发起时串行化：
第二个请求会看到第一个已建的 `RUNNING` 记录并直接返回，不会撞 `contract_id` 唯一约束。

## Mock 模式增强（顺带）

原来的 mock 返回写死的风险片段，与合同原文对不上，导致原文高亮和版本闭环都看不出效果。
现在 mock 会**从合同原文里按关键词截取真实段落**作为 `contract_snippet`，四个维度（付款/违约/争议/结构）各取不同段落，总体风险按高风险条数规则计算。

## 已知限制

1. **流式追问的 token 统计为 0**：OpenAI 流式协议默认不返回 usage，需开启 `include_usage`。
2. **问题闭环是规则判定**：靠片段匹配 + 文本相似度，不做语义理解。改写幅度大时会判为"疑似已修复"而非"已改写"，属于保守策略，界面已提示需人工确认。
3. **限流是进程内计数**：多 worker 部署时各进程独立计数；需要严格全局限流可换 Redis 计数（`rate_limit.py` 已预留结构）。
4. **版本比对没有做语义 diff**：只做段落级文本差异，不识别"换了个说法但意思一样"。
